# Model card: BM25 retriever and stub reader

A model card for the retrieve-then-read pipeline that ships with this lab. Labs built from
it should copy this structure for every retriever and reader they gate on.

## Pipeline details

| Field | Value |
|---|---|
| Retriever | `BM25` (Okapi BM25, k1=1.5, b=0.75) over whitespace-token chunks, ported from ailab-evals |
| Baselines | `random` (seeded shuffle) and `lead` (first chunk of each document) |
| Reader | `Reader` with cite-or-refuse, default backend `StubProvider` (model id `stub-reader-v1`) |
| Live reader | `OllamaProvider` records a cassette; `ReplayProvider` replays it offline |
| Version | v1 (package 0.1.0) |
| Owner | Andrew Pyle |
| License | Apache-2.0 |
| Inputs | A natural-language question and a chunked corpus |
| Outputs | A ranked list of chunk ids, then an answer with cited chunk ids, or a refusal |

## Intended use

- Primary: a reference RAG pipeline that demonstrates a retrieval gate, a cite-or-refuse
  reader, and honest generation checks.
- Users: engineers learning RAG evaluation, or building a lab from this template.
- Out of scope: answering real user questions, any decision affecting a person, any corpus
  other than the synthetic Nimbus one, and any claim that the stub reader understands text.

## Data

- Corpus: `fixtures/nimbus_corpus.jsonl`, 20 synthetic documents about a fictional SaaS
  named Nimbus. Provenance and sha256 in [FIXTURES.md](FIXTURES.md).
- Questions: `fixtures/nimbus_questions.jsonl`, 18 questions with span-keyed ground truth.
- No real product, support, or personal data.

## Metrics

| Metric | Why |
|---|---|
| recall@k | Of a question's relevant chunks, how many the retriever found |
| hit@k | Whether any relevant chunk reached the reader |
| MRR | How high the first relevant chunk ranks |
| nDCG@k | Rank quality against the ideal ordering |
| critical recall@k | Recall on the questions marked critical |
| citation_resolvable | Whether cited ids exist in the retrieved set (a format check, not faithfulness) |
| lexical_support | n-gram overlap between the answer and its cited chunk |
| refusal_correct / false_refusal / wrong_refusal | Cite-or-refuse behaviour on answerable and unanswerable questions |

Gate (in `eval_config.toml`): recall >= 0.70, hit >= 0.70, MRR >= 0.50, nDCG >= 0.55, all
with a 0.05 tolerance band, plus the baseline, saturation, refusal, and support checks.

### Real reader (gemma3:27b, replayed from the committed cassette)

The Reader seam was exercised by a real model, not only the stub. A cassette of `gemma3:27b`
completions was recorded with `make record` and replayed with `ailab-eval --provider replay`.
The retrieval metrics are identical (retriever-only); the generation checks differ:

| Metric | Stub | gemma3:27b (real) |
|---|---|---|
| citation_resolvable | 1.0000 | 1.0000 |
| lexical_support | 1.0000 | 0.8457 |
| refusal_correct / false_refusal / wrong_refusal | 4 / 0 / 0 | 4 / 0 / 0 |
| answered | 14 | 14 |

The real `lexical_support` of 0.8457 is below the stub's 1.0 because the model paraphrases
the cited chunk rather than copying it. The real record is in `results/replay_gemma3.json`.
The real model echoed the context bracket format on some citations (`[chunk#id]`); the
Reader parser strips one surrounding pair, which is why `citation_resolvable` stays 1.0.

## Limitations

- recall@5 is below 1.0 because one question (`q07`) has a second relevant chunk excluded by
  the top-k cutoff. This is expected and is the worked example in the learning notes.
- The stub reader is a FORMAT path. Its `lexical_support` of 1.0 reflects that it copies the
  answer from the chunk it cites, not that it reasons.
- The lexical cite-or-refuse rule refuses the near-miss unanswerable questions only because
  each carries a word absent from the corpus. It would not refuse a near-miss that shares
  every word. A real reader is needed for that. The recorded `gemma3:27b` pass shows the
  same refusal counts, because refusal is decided before the reader is called.
- A 18-question set exercises the gate. It is not large enough to compare close systems.

## Ethical considerations

- The data is synthetic and contains no personal information, so no consent issue arises.
- A real RAG assistant answers people's questions. A confident wrong answer to an
  unanswerable question (a wrong refusal) can mislead. This lab reports that rate and gates
  it to zero on the canonical run.
- Before trusting a reader on real users, evaluate it on representative, consented,
  appropriately licensed data, and record faithfulness with a model that reads for meaning.

## Caveats and recommendations

Treat BM25 and the stub reader as a floor and a demonstration. Before replacing BM25, keep
the baselines in every table. The recorded `gemma3:27b` pass exercises the reader seam with a
real model; before trusting the reader in production, add a real faithfulness judge that
reads for meaning rather than counting n-grams.
